# 产品架构 — 三大产品形态总览

> 本文档定义 Nexus-Rust 工作台的**三大产品形态**及其 UI / 状态 / 后端职责划分。
> 这是 [spec-plan.md](./spec-plan.md) 的配套设计文档,阶段 1-6 都遵循此架构。

---

## 三大产品形态

```
┌─────────────────────────────────────────────────────────────┐
│                  Nexus 工业通信工作台                        │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐          │
│  │ ① 主站      │  │ ② 从站      │  │ ③ 串口调试  │          │
│  │ Master      │  │ Slave       │  │ Serial Debug│          │
│  │ (Poll)      │  │ (Simulator) │  │ (Terminal)  │          │
│  └─────────────┘  └─────────────┘  └─────────────┘          │
│        │                │                 │                  │
│        └────────────────┼─────────────────┘                  │
│                         ▼                                    │
│  ┌─────────────────────────────────────────┐                 │
│  │ ④ 报文解析 (Frame Parser)               │  ← 工具型,横切  │
│  └─────────────────────────────────────────┘                 │
└─────────────────────────────────────────────────────────────┘
```

| 形态 | 类比 | 角色 | 数据方向 | 主要交互 |
|---|---|---|---|---|
| **① 主站** | Modbus Poll | 客户端,主动读写 | 发请求 → 收响应 | 读/写/扫描/轮询 |
| **② 从站** | Modbus Slave | 服务端,被动响应 | 收请求 → 发响应 | 赋值/置零/监听 |
| **③ 串口调试** | HSL 调试助手 | 透明收发终端 | 双向原始字节 | hex 发送/接收/加校验 |
| **④ 报文解析** | (横切工具) | 离线/在线解析 | 输入 hex → 输出结构化 | 粘贴报文 → 解析字段 |

## ① Modbus 主站 (Modbus Master)

### 定位
主动向从站设备发起读写请求的客户端。对标 Modbus Poll / HSL `UserControlReadWriteDevice`。

### 功能清单

**基础配置区**:
- 站号(1–247,broadcast 0 仅写)
- 功能码选择(FC01–06、08、15、16、22、23、43)
- 地址(支持十进制 / `0x` 十六进制 / 5 位前缀 `0xxxx`/`1xxxx`/`3xxxx`/`4xxxx`)
- 数量(读:1–2000 线圈 / 1–125 寄存器;写:相应上限)
- 数据类型(UInt16/Int16/UInt32/Int32/Float32/Float64/String)
- 字节序(ABCD/DCBA/BADC/CDAB)
- 超时(1–600000 ms)

**连接方式选择**:
```
┌─ 连接方式 ─────────────────────────────────────┐
│ ○ RTU 串口    [COM3 ▼] [9600 ▼] [8/N/1 ▼]    │  ← RS-232 / RS-485
│ ○ ASCII 串口  [COM3 ▼] [9600 ▼] [8/N/1 ▼]    │
│ ○ TCP         [192.168.1.5] [502] [站号 1]    │  ← 网口
│ ○ UDP         [192.168.1.5] [502] [站号 1]    │
│ ○ RtuOverTcp  [192.168.1.5] [502] [站号 1]    │
│ ○ AsciiOverTcp[192.168.1.5] [502] [站号 1]    │
└───────────────────────────────────────────────┘
```
> 注:RS-232 和 RS-485 在软件层都是 RTU/ASCII 串口,差别在电平(硬件),UI 上用"串口模式"单选区分即可。

**指令操作区**:
- 读取一次(单次 FC01–04)
- 写入一次(单次 FC05/06/15/16)
- 连续轮询(周期性读,间隔可配)
- 停止轮询

**扫描区**(阶段 2):
- 扫描站号(遍历 1–247,探测在线从站)
- 扫描波特率(遍历常用波特率,探测设备响应)

**结果显示区**:
- 寄存器/线圈表格(地址 / 区域 / 数据类型 / 字节序 / 值 / 质量 / 时间戳)
- TX/RX 报文追踪(方向 / 站号 / FC / hex 字节 / CRC / 耗时 / 结果)
- 告警记录(错误码 / 消息 / 建议)

### 后端职责
| 层 | 职责 |
|---|---|
| **渲染层** | 表单状态、表格渲染、trace/alarm 追加 |
| **Electron 主进程** | IPC 分发、串口句柄持有(RTU/ASCII 路径)、Rust 侧车生命周期 |
| **Rust core** | 帧构建(CRC/LRC/MBAP)、帧解析、值编解码、TCP/UDP socket 持有 |

## ② Modbus 从站模拟 (Modbus Slave)

### 定位
模拟从站设备,被动响应主站请求。对标 Modbus Slave 软件 / HSL `FormModbusServer` / .NET `ModbusTcpSimulator`。

### 功能清单

**监听配置**:
```
┌─ 监听模式 ─────────────────────────────────────┐
│ ○ TCP 监听    [端口 502] [允许站号 1,2,3-10]  │
│ ○ RTU 串口    [COM5 ▼] [9600 ▼] [站号 1]      │
│ ○ ASCII 串口  [COM5 ▼] [9600 ▼] [站号 1]      │
└───────────────────────────────────────────────┘
```

**内存区管理**(4 个区):
- 线圈(Coils,0xxxx)— 65536 位
- 离散输入(Discrete Inputs,1xxxx)— 65536 位
- 输入寄存器(Input Registers,3xxxx)— 65536 字
- 保持寄存器(Holding Registers,4xxxx)— 65536 字

**基础操作**:
- **赋值**:对指定地址/范围写入预设值(批量填充、随机、递增、正弦波等模式)
- **置零**:整区或指定范围清零
- **指令设置**:配置自动响应行为(异常码注入、延迟模拟、值变化触发)

**客户端会话**(TCP 模式,对标 HSL):
- 在线客户端列表(IP / 端口 / 连接时间 / 最后请求)
- 在线计数

**流量日志**:
- 收到的请求帧(站号 / FC / 地址 / 数据)
- 发出的响应帧(正常 / 异常)
- 异常注入记录

### 后端职责
| 层 | 职责 |
|---|---|
| **渲染层** | 内存区表格(可编辑)、会话列表、流量日志 |
| **Electron 主进程** | IPC 分发、串口句柄(RTU 从站路径) |
| **Rust core** | `TcpListener` 接受连接、请求分发、响应生成、内存区管理 |

### 关键决策
- **TCP 从站**:Rust core 持 `TcpListener`,每客户端一线程,共享内存区。
- **RTU 从站**:Windows 上 COM 口独占 —— Electron 打开句柄,Rust 通过 JSONL 指令告诉 Electron "读到 N 字节就回调我"。(架构挑战,详见 [phase-3-modbus-slave.md](./phase-3-modbus-slave.md))

## ③ 串口调试 (Serial Debug)

### 定位
透明收发原始串口字节的终端工具。对标 HSL `FormSerialDebug` / `DebugControl`。这是唯一允许渲染层提交任意字节的模式。

### 功能清单

**串口配置**(复用主站连接表单):
- 端口 / 波特率 / 数据位 / 停止位 / 校验 / 流控 / DTR / RTS

**发送区**:
```
┌─ 发送 ─────────────────────────────────────────────────┐
│ [hex 输入框,如: 01 03 00 00 00 0A C5 CD           ] │
│ [发送] [清空] [勾选☐自动追加 CRC] [勾选☐自动追加换行] │
│ 发送模式: ○ ASCII  ○ HEX  ○ Modbus RTU(自动CRC)     │
└───────────────────────────────────────────────────────┘
```

**收发控制**(HSL 风格):
- ☐ 允许接收(开关)
- ☐ 允许发送(开关)
- ☐ 加校验(自动追加 CRC-16 / LRC)
- ☐ 显示时间戳
- ☐ 自动换行(按帧/按超时)
- 接收超时帧间隔(默认 3.5 字符时间)

**接收区 / 流量显示**:
```
┌─ 收发记录 ─────────────────────────────────────────────┐
│ 时间          方向  hex                                    解析           │
│ 14:32:01.123  TX    01 03 00 00 00 0A C5 CD              FC03 读保持    │
│ 14:32:01.245  RX    01 03 14 00 64 ... CRC=OK            10个寄存器     │
│ 14:32:02.001  TX    01 06 00 05 00 FF C8 32              FC06 写单寄存器│
└─────────────────────────────────────────────────────────┘
```

**校验工具**:
- CRC-16/MODBUS 计算器(输入 hex → 输出 CRC)
- LRC 计算器(ASCII 模式)
- 校验状态自动判定(收到帧的 CRC 是否正确)

**报文解析**:
- 点击任意一行流量 → 右侧解析面板显示字段拆解(对标 .NET `ModbusPacketParser`)
- 或独立"报文解析"tab,粘贴 hex → 解析

### 后端职责
| 层 | 职责 |
|---|---|
| **渲染层** | hex 输入、流量表格、校验工具 UI |
| **Electron 主进程** | 串口句柄、收发循环、帧分隔(超时/字符间隔) |
| **Rust core** | CRC/LRC 计算、Modbus 报文解析(可选,解析走 Rust 保证一致性) |

### 关键决策
- 串口调试模式下,**渲染层可以提交任意字节**(这是唯一例外,通过明确的模式切换保护)。
- 收发循环在 Electron 层(`serial-service.cjs` 扩展),Rust 只做校验计算和报文解析。
- 帧分隔用"3.5 字符时间"规则(RTU 标准)或可配超时。

## UI 架构(多 view 切换)

### 当前状态
`index.html` 的 `.module-tabs nav` 已有 4 个 tab 按钮,但只有"主站"有内容:

```html
<div class="module-tabs">
  <div class="session-tab"><i></i><strong>Modbus RTU</strong></div>
  <nav aria-label="Modbus 功能">
    <button class="is-active" type="button">主站</button>
    <button type="button" disabled>从站模拟</button>   <!-- ← 激活 -->
    <button type="button" disabled>串口调试</button>   <!-- ← 激活 -->
    <button type="button" disabled>报文解析</button>   <!-- ← 激活 -->
  </nav>
</div>
```

### 目标布局

```
.module-shell (3 行 grid)
├── Row 1: .module-tabs          ← tab 栏(已有)
├── Row 2: .connection-pane      ← 连接配置(已有,共享给所有 view)
└── Row 3: [view 切换区]          ← 根据 activeView 显示
            ├── <section data-view-panel="master">       ← 主站工作区(已有 #workspace)
            ├── <section data-view-panel="slave" hidden> ← 从站工作区(新建)
            ├── <section data-view-panel="debug" hidden> ← 串口调试工作区(新建)
            └── <section data-view-panel="parser" hidden>← 报文解析工作区(新建)
```

### view 切换逻辑

复制现有 `activateConsole()` 模式(main.js:444),新增 `activateView(viewName)`:

```javascript
function activateView(viewName) {
  for (const tab of elements.viewTabs) {
    const selected = tab.dataset.view === viewName;
    tab.classList.toggle("is-active", selected);
    tab.setAttribute("aria-selected", String(selected));
  }
  for (const panel of elements.viewPanels) {
    const selected = panel.dataset.viewPanel === viewName;
    panel.classList.toggle("is-active", selected);
    panel.hidden = !selected;
  }
  activeView = viewName;
  syncActionState();  // 不同 view 的按钮启用规则不同
}
```

### 连接区共享问题

`.connection-pane`(#serial-form)在所有 view 之间共享 —— 但不同 view 需要不同字段:
- **主站**:端口 / 波特率 / 站号 / 数据位 / 校验 / 停止位 / 流控
- **从站**:端口 / 波特率 / 站号 / 数据位 / 校验 / 停止位 / 流控(相同)
- **串口调试**:同上(相同)
- **报文解析**:不需要连接(离线工具)

**方案**:连接区保持共享(行 2),切换到"报文解析"时隐藏连接区或禁用。切换到 TCP 模式时(阶段 1)连接区内容换成 IP/端口/站号。

## 状态管理

### 当前(全局变量)
```javascript
let busy;                          // 单一操作锁
const stats = { tx, rx, ... };     // 计数器
// connectionPill.dataset.state     // closed | open | error
```

### 目标(按 view 隔离)
```javascript
let activeView = "master";         // master | slave | debug | parser

const masterState = {
  busy: false,
  connection: { transport: "rtu", ... },
  poll: { active: false, intervalMs: 1000, ... },
};

const slaveState = {
  running: false,
  listenMode: "tcp",               // tcp | rtu | ascii
  port: 502,
  memory: { coils: [...], holding: [...], ... },
  sessions: [],                    // TCP 客户端会话
};

const debugState = {
  allowReceive: true,
  allowSend: true,
  appendCrc: false,
  sendMode: "hex",                 // hex | ascii | modbus-rtu
  frames: [],                      // 收发记录
};
```

### 锁的协调
当主站和从站**共享一个串口**时(不可能 —— Windows COM 独占),或**各自独立端口**时:
- 主站和从站不能同时打开同一个 COM 口。
- 用全局 `serialLock` 协调:切换 view 时检查端口占用状态。

## Rust core 架构演进

### 当前(纯 codec,无状态)
```
serve() → handle_line(line) → CommandOutcome  (纯函数)
```

### 目标(会话状态,阶段 1 引入)
```
serve(session: &mut Session) → handle_line(session, line) → CommandOutcome

Session {
  connections: HashMap<ConnectionId, Connection>,
  slaves: HashMap<SlaveId, SlaveServer>,
  poll_streams: HashMap<StreamId, PollStream>,
}

Connection {
  transport: Transport,           // Tcp | Udp | Serial(Rtu|Ascii)
  socket: TcpStream | UdpSocket,
  unit_id: u8,
  byte_order: ByteOrder,
}
```

### 模块划分(最终形态)
```
rust-core/src/
├── lib.rs                  ← serve() + Session
├── protocol.rs             ← JSONL 分发
├── error.rs                ← 错误码
├── serial_config.rs        ← 串口校验
├── modbus_rtu.rs           ← RTU 帧 + CRC16 (已有)
├── modbus_ascii.rs         ← ASCII 帧 + LRC (阶段 1)
├── modbus_tcp.rs           ← MBAP 帧 (阶段 1)
├── modbus_pdu.rs           ← PDU 构建/解析(所有 FC,传输无关) (阶段 1)
├── value_codec.rs          ← 多数据类型 + 字节序 (阶段 2)
├── modbus_master.rs        ← 主站事务编排(端到端) (阶段 1)
├── modbus_slave.rs         ← 从站服务器(响应生成) (阶段 3)
└── frame_parser.rs         ← 离线报文解析 (阶段 6)
```
