# Phase C Roadmap — Stub Protocol Deepening

This document is the authoritative list of protocol libraries in `src/` that
need deepening from stub to usable implementations. Generated by a full audit
of every `src/Nexus.*/` directory (see Phase B commit history).

## Priority 1 — True protocol gaps (real user demand)

These stubs advertise functionality they do not provide. Real devices exist
in the field; users will hit the "暂不支持" message and have no workaround.

| Library | Current state | Recommended implementation | Effort |
|---|---|---|---|
| `Nexus.Xinje.Serial` | ✅ **DONE in Phase C-1** — Xinje XC/XD Modbus RTU compatible client. Inherits ModbusRtuClient, adds X/Y/M/S/D/HD address mapping. 37 tests. | — | Done |
| `Nexus.Delta.Ascii` | ✅ **DONE in Phase C-2** — Delta DVP Modbus ASCII compatible client. Inherits ModbusAsciiClient, adds X/Y/M/S/T/C/D address mapping. 29 tests. | — | Done |
| `Nexus.Siemens.WebApi` | Stub, wrong base class (TcpDeviceBase for an HTTP protocol) | Re-implement on HttpClient + JSON parsing. S7-1200/1500 Web API uses `GET /api/json/reads?var=...` returning JSON. Needs BASIC auth. | 3-5 days |
| `Nexus.Mitsubishi.IqR.Serial` | Stub, returns Failed | MELSEC iQ-R over RS-232 — basically MC3E binary framing over serial. Reuse existing MC3E Binary frame builder. | 2-3 days |
| `Nexus.Mitsubishi.ASeries` | Stub | Mitsubishi A-series (FX3U-era) computer link protocol. ASCII frames with STX/ETX. | 3-5 days |

**Effort estimate:** ~2 weeks total for the remaining 3.

## Priority 2 — Brand wrappers needing verification

These inherit a parent protocol (Modbus/CIP) and add nothing. They are
"intentional" in the sense that they provide a brand entry point + NuGet
package, but the question is whether the real device deviates from the parent
protocol.

| Library | Parent | Action |
|---|---|---|
| `Nexus.BoschRexroth` | AllenBradley CIP | Verify CtrlX actually uses standard EtherNet/IP CIP; if so, leave as-is. If deviations exist, override specific methods. |
| `Nexus.Hitachi` | ModbusRtuOverTcp | Confirm Hitachi EH-150 uses standard Modbus RTU framing. |
| `Nexus.Honeywell` | ModbusTcp | Confirm Honeywell HC900 uses standard Modbus TCP. |
| `Nexus.Toshiba` | ModbusTcp | Confirm Toshiba uses standard Modbus TCP. |
| `Nexus.Delixi` | ModbusRtu (DTSU6606) | Already has DTSU6606-specific register map. Solid, no action needed. |

**Effort:** 1-2 days of device manual reading + maybe one verification test each.

## Priority 3 — Pure Modbus packaging wrappers (NO action needed)

These exist purely to provide a separate NuGet package entry point. They are
intentional and not bugs.

| Library | Why it exists |
|---|---|
| `Nexus.Modbus.Ascii.Serial` | "Modbus ASCII over serial" as standalone package |
| `Nexus.Modbus.Rtu.Serial` | "Modbus RTU over serial" as standalone package |
| `Nexus.Modbus.AsciiOverTcp` | "Modbus ASCII over TCP" as standalone package |
| `Nexus.ModbusPlus` | Branding variant |

**Action:** none. Keep as-is.

## Recommended migration path

When deepening a stub, prefer the **Phase B new bases**:

1. For TCP/serial/UDP protocols: inherit `DeviceTcpNet` / `DeviceSerialPort` /
   `DeviceUdpNet` instead of the legacy bases.
2. Provide an `INetMessage` for frame parsing.
3. Inherit `DeviceServer` for the integration-test virtual server.

See `docs/PHASE_B_MIGRATION_NOTES.md` for step-by-step guidance and
`src/Nexus.LengthPrefixTcp/` for a minimal reference implementation.

The legacy bases (`TcpDeviceBase`/`SerialDeviceBase`/`UdpDeviceBase`) are
marked `[Obsolete]` (Phase B8) — new stub deepening should not use them.
